## Executive summary

**Verdict.** The architecture is the strongest answer to this brief I would expect to see:
- a real agent loop;
- facts written by tools, with evidence levels;
- a deterministic gate and chain calculator;
- deadline-aware waits;
- a backtested meta-loop.

The vehicle-warning card is close to Bahn's own example.

What will lose points is the gap between what the card promises and what the system does:
- **Approval is not what gets executed.**
  - A "new driver" plan booked the ferry and hotels at once and texted the plan to the driver who had just been ruled out.
  - A gate-blocked option can still be approved through Edit.
  - The Edit box "What should change" (placeholder: "no Helsinki nights") is silently ignored when the plan runs.
- **Failures fall into a black hole.** A failed run, a rejection, an expired card or a Jev error leaves nothing in front of a person.
- **The differentiators are invisible.**
  - No card has ever shown a blocked option.
  - Every live gate catch so far was a clock artefact.
  - The 4/4 / 0/6 result lives only in a test, and it is narrower than it sounds.

The demo data is also contaminated (future-dated decisions, a booked train the operator rejected, stale triage cards), and there is no README.

**Top 5 fixes before the demo:**
1. **Execute only what was approved** (B1, B4, H6).
   - Steps that wait on a new driver become MANUAL.
   - The server refuses blocked options, and so does Edit.
   - A free-text change re-plans instead of being ignored.
   - No customer text after a failed booking; no booking of a departed sailing.
2. **Hand-over card everywhere** (B2). One `handOver()` that opens a TRIAGE card on run failure, reject, expiry and Jev failure. Also stop treating ESCALATED runs as active.
3. **A clock and dedupe the demo cannot trip on** (H1, H2, H3).
   - Waitpoint token with a 24 h real timeout; expire cards on sim time instead.
   - Add the signal id to the Trigger idempotency key.
   - `reset` deletes the order's signals and `msg-sim-*` messages.
   - Then one `demo:reset` and fresh cards for each playbook.
4. **Make the gate visible and claim it honestly** (H4, H5).
   - Render `firstPass` violations in plain words on the card.
   - Add a "Bahn's 14 recorded proposals" panel on `/playbooks`.
   - Add held-out reworded tests before saying "4/4" on video.
5. **README, `.env.example`, a portable `CLAUDE_BIN`, commit and push** (B3). Without these the submission fails the brief's fresh-clone rule.

### B1 (blocker): approving a conditional plan executes it unconditionally and messages the wrong driver

**Evidence.** CD-420154, card `c637c39a…`. Checked with SQL on `control.cards.options` and the `execute` block_runs.

Option A's actions:

| Action | Type | Text |
|---|---|---|
| A1 | MARKET | "Publish a new offer … Keep Jonas's assignment until a replacement accepts" |
| A2 | BOOK_TRAVEL | "Book the Sat 24 Oct ferry **once a new driver has accepted**" |
| A3, A4 | BOOK_TRAVEL | hotels |
| A5 | INSTRUCT_CHANGE | "Send the plan **to the new driver** once bookings succeed" |

What execution did:
- A2, A3 and A4 ran at once and wrote BOOKED facts.
- A1 became MANUAL.
- A5 was sent to **Jonas Haverforde**, the driver the operator had just ruled out.

The same card's "The agent will not" list says: "Book any ferry, hotel or train before a yes and before a new driver has accepted". See `public/brand/screens/decision-card-after-approve.png`, "What happens next".

Where in the code:
- `lib/playbooks/blocks/execute.ts:106-123` books every BOOK_TRAVEL action and sends every message. It has no notion of a condition.
- `lib/playbooks/bahnWrites.ts:32-38` resolves "driver" to the current assignment.

**Why it matters.** This is the rule Bahn put in bold, and the system breaks its own written promise on the same screen. It also contradicts SUBMISSION.md ("Nothing that touches a booking … happens without a yes").

**Smallest fix.**
- In `executeActions`: when the option contains a MARKET action or a `REPLACE_DRIVER` change, mark BOOK_TRAVEL and driver-message actions as `MANUAL` with "Waits for the new driver to accept".
- In `lib/playbooks/blocks/gate.ts`: treat an action description matching `/\b(once|after|when)\b.*\b(accept|confirm)/i` on an executable action class as a violation, so the agent splits it out.

### B2 (blocker): failures, rejections, expiries and Jev errors leave nothing in front of a person

- **(a) Failed run.**
  - An agent timeout, CLI error or rate limit sets the run to FAILED and rethrows (`lib/playbooks/runtime.ts:184-187`). No card is created.
  - "Agents on it" lists only `ACTIVE_RUN_STATUSES` (`lib/control-room/home.ts:22-28`), so the order quietly becomes "quiet".
  - The comment at `lib/playbooks/task.ts:16` says failures go to a person. They don't.
  - Tools may already have messaged the driver.
- **(b) Reject or expiry.**
  - `escalate` only returns `{ outcome }` (`playbooks/missed-ferry/steps.ts:195-202`; the same in all four playbooks).
  - Home then shows "Rejected by damir · **Handed to a person**" with a **green check** (`components/control/QueueRows.tsx:194`). No person has it.
  - An EXPIRED card simply leaves "Needs your decision". The deadline passed, and the order goes quiet. The card itself shows it in neutral grey (`components/control/CardView.tsx:27`).
- **(c) An escalated run swallows later signals.**
  - The watchman treats ESCALATED as active: `lib/watchman/dispatch.ts:37` excludes only CLOSED and FAILED.
  - Every later message on that order is "attached" to the dead run (`lib/watchman/inspect.ts:131-134`), and the same playbook is deduped forever (`dispatch.ts:66-67`).
  - This is live now on CD-420154 (missed-ferry, ESCALATED) and CD-420442 (pickup-unconfirmed, ESCALATED). S1 injected on CD-420154 would do nothing.
- **(d) Jev failure.**
  - The signal is routed to `record`, with no card (`inspect.ts:216-240`, `routing.ts:114-121`).
  - A retry then skips it: "message already inspected".
- **(e) Folded triage card.**
  - A new decision card cancels the order's triage card (`lib/playbooks/cards.ts:41-44`).
  - It is never reopened after a reject or expiry.

**Why it matters.** The brief asks "what happens when something goes wrong" and wants the agent to "hand over with what it found". Today a judge who clicks Reject sees the order vanish.

**Smallest fix.**
- Add `handOver({ orderId, runId, reason, factIds })` in `lib/playbooks/cards.ts`. It opens a TRIAGE card titled with the reason, for example:
  - "Agent stopped: Claude timed out after 12 min";
  - "You rejected the options: <note>";
  - "Nobody decided before 23:00".
- Call it from the `runtime.ts` catch, from every `escalate` step, and from the watchman's Jev-failure path for messages.
- Add `'ESCALATED'` to `ACTIVE_RUN_EXCLUDED` in `dispatch.ts:37`.
- Use a cross icon for Rejected and Expired in "Decided recently".

### B4 (blocker): the approve path does not respect the gate, and Edit's free-text change is silently dropped

- **(a) A blocked option can be approved.**
  - When no option is approvable, Edit starts from `options[0]` (`components/control/DecisionActions.tsx:31`), and its submit stays enabled (`:156`). That option is blocked, so a note plus a reason approves a blocked option.
  - The server never checks:
    - `decideCard` accepts any `optionId` (`lib/control-room/actions.ts:89-121`);
    - `applyDecision` takes any id and falls back to `options[0]` (`lib/playbooks/decision.ts:50-62`);
    - the spike's shorthand `{decision:'approve'}` is still accepted (`decision.ts:25-32`);
    - nothing re-gates the edited option (`lib/playbooks/blocks/human.ts:97`).
  - So a customer text the gate blocked under G3 or G4 is sent by `execute.ts:29, 76`.
  - This contradicts `/playbooks`: "An option that breaks one is shown as blocked and cannot be approved as is" (`app/playbooks/page.tsx:144-145`).
- **(b) The free-text change is never applied.**
  - The Edit form's "What should change" textarea has the placeholder "e.g. book the cheaper hotel, no Helsinki nights" (`DecisionActions.tsx:139-145`).
  - `applyDecision` applies only `removeActionIds` and `messages` (`decision.ts:53-61`). `edits.note` is read only by the meta-loop (`lib/meta/load.ts:76`, `store.ts:41`).
  - So the operator writes "no Helsinki nights", the card says "Approved with changes", and the Helsinki nights are booked.

**Smallest fix.**
- In `decideCard`, refuse an option that fails `isApprovable` (`lib/control-room/options.ts:195-197`).
- In `human.ts`, re-run `checkOption` on the edited option and return no option if it still violates a rule.
- Start Edit from `primary` only.
- For (b), either:
  - loop back: when `edits.note` is set, call `ctx.services.rerunAgent({ blockId: optionsFrom, feedback: note })`, re-gate, and issue a new card; or
  - the minimum: relabel the field "Note for the playbook (not carried out)" and keep only "drop a step" and "edit a message" as executable edits.

### H1 (high): the waitpoint token's timeout is fixed in real time when the card is created

**Evidence.**
- `lib/playbooks/blocks/human.ts:18-33, 50`: timeout = decide-by converted to real time at the speed at creation, with a floor of 15 real minutes.
- A card created at 30× or 120× gets about 15 real minutes. If the presenter pauses to talk, the countdown freezes but the token still dies. The card flips to "Expired, nobody decided", and then B2(b) applies.
- At 120× the opposite happens: the card stays decidable long after its decide-by, and approving it can book a ferry that already sailed (H6).
- Clicking Approve after the token expired shows "This card was already decided" (`actions.ts:78`), which is false.
- If the worker has not yet processed the timeout, `decideCard` claims the card and says "Sent". Then `human.ts:73` overwrites it to EXPIRED with no status guard.

**Fix.**
- Always create the token with a 24 h real timeout and expire cards on sim time from the watchman tick.
- Call `wait.retrieveToken` before claiming in `decideCard`.
- Make `human.ts:73` an `updateMany` with `where: { status: 'OPEN' }`.

**If there is no time:** create demo cards with the clock **paused** (the 24 h fallback applies) and never change speed while a card is open.

### H2 (high): rehearse, then record within 30 minutes, and nothing runs

**Evidence.**
- `lib/watchman/dispatch.ts:68-76` dedupes on any signal from the last 30 **real** minutes that triggered the same playbook.
- `dispatch.ts:112-117` also sets a global Trigger idempotency key `watchman:<orderId>:<playbookId>` with a 30-minute TTL. Inside that window Trigger returns the **old, finished** run.
- `scripts/playbooks/reset.ts:55-58` deletes only monitor signals dated after sim now; message signals stay.
- Reset also leaves injected `msg-sim-*` messages; it only deletes `msg-ctl-*` (`:21-24`). The next run therefore also sees the rehearsal's driver message as a fact.
- At 120×, 30 real minutes is 60 sim hours, so real follow-up signals are swallowed too.

**Fix.**
- Key on `watchman:<orderId>:<playbookId>:<signalId>`, or drop the Trigger key and rely on `findActiveRun`.
- In `reset.ts`, delete the order's signals and its `msg-sim-*` messages and conversations.

**Workaround:** leave 30 real minutes between the last rehearsal and the recording, or use a fresh order.

### H5 (high): the 4/4 / 0/6 claim is narrower than it sounds, and the live agents never reach the code that earns it

- `mark_boarding_confirmed` (`lib/gate/forbidden.ts:110`);

### M1 (medium): the decide-by reason can contradict the options, or lie in the past

**Evidence.**

### M2 (medium): the chain anchors on a slot end that is already past (the S3 situation)

**Evidence.**
- `compute.ts:222`: with the car not collected after the slot ended, NO_CHANGE's ETA is slot end + drive, which inflates slack.
- `:755`: `leaveAt = slotEnd`, a past time, so unreachable sailings count as feasible.
- `:743, 757-759`: NEW_SAILING stays feasible after its cutoff when road time is unknown or the cutoff is null.

**Fix.**
- Use `max(now, slotEnd)`.
- Add `checkInCutoffAt <= now → infeasible`.

### M3 (medium): the wait block ignores clock changes after it starts

**Evidence.** `lib/playbooks/waitDuration.ts:41-42` and `adapters/trigger.ts:19-23` convert sim minutes to real time once, at the start speed.
- "Jump ahead 1 hour" and 1×→120× do not wake the run.
- A paused clock sleeps the sim minutes as real minutes.
- Home shows "Waiting until 11:05" after 11:05 has passed.
- The inline adapter caps the wait at 10 s, yet the card says "waited 75 min".

**Fix.** Sleep in chunks of at most 60 s and re-read the clock until `until`.

### M4 (medium): two playbooks can run on one order at once

**Evidence.**
- `decideRoute` dispatches every playbook above its threshold (`lib/watchman/routing.ts:79-83`).

### M5 (medium): evidence holes in the ladder and the projection (where facts come from)

**Requirements missing a filter** (`lib/evidence/ladder.ts`):

| Requirement | Wrongly satisfied by | Where |
|---|---|---|
| `NOT_BOOKED` | a reconciliation that says `BOOKING_EXISTS` | `:634`; `askProvider.ts:30` also writes `NOT_FOUND` as OBSERVED |
| `HOTEL_BOOKED` | a cancelled reservation, since reservations project at BOOKED whatever their status | `:641`; `projection.ts:321` |
| `PROMISE_CHANGED` | any customer approval, including the original `promise_recorded`, so G6 passes | `:803`; `check.ts:454` |
| `DRIVER_LOCATION_VERIFIED` | any OPERATOR_DECISION, which `human.ts:114` writes at VERIFIED for every decision, rejects included | `:725` |

**The projection overstates or invents.**
- 17 superseded customer promise windows stay at BOOKED and still count as customer approval (`lib/facts/projection.ts:166-170`).
- `add()` fills a missing time with the order's creation time (`projection.ts:78`). 321 of 351 windows have no `stated_at`, so **cards show a made-up time** and the gate sees the fact at any `now`.

**Writes are not tied to approvals.**
- `writeFact` caps only AGENT_INTERPRETATION (`lib/facts/store.ts:158-170`).
- BOOKED tool facts carry no link to the approving card (`quotes.ts:136`, `simulated.ts:93`).

**The UI and the ladder define levels differently.** `components/ui/evidence.ts:14-22` vs `ladder.ts`. For example, the UI says BOOKED means "Reserved with a reference", which is what a customer-agreed promise-window chip then tells a judge.

**Fix.**
- Add the `where` filters.
- Project superseded windows at STATED.
- Mark missing times as unknown instead of inventing them.
- Require a decision fact id for any tool write at BOOKED or above.
- Import levels and meanings from `@/lib/evidence/ladder`; it is client-safe.

### M6 (medium): simulated replies are labelled as Bahn records

**Evidence.**

### M7 (medium): the meta-loop's backtest can approve meaningless or loosening changes

All verified by the meta sub-review with read-only scripts.

**Loosened settings pass.** Only "newly blocks an approved option" can fail a case, and an empty case set counts as improved (`lib/meta/backtest.ts:332, 443, 503, 551, 590-603`). Results:
- loosening G5 from 90 to 240 min passes, with 0 of 30 cases failing;
- `maxOptions` 3→1 passes with **0 cases**;
- `decisionMarginMinutes` 30→240 passes with **0 cases**.

The proposer prompt says "never loosen a guardrail" (`propose.ts:19`), yet the whitelist allows G5 up to 240 (`whitelist.ts:20-23`).

**"Follows the correction" is a single sample.**
- The "before" is the recorded output, while the "after" is a replay in a different mode, with tools off.
- Jev gets the operator's note verbatim (`judge.ts:45-49`), so an amendment that restates the note scores high. The approved `e6a8065f` is close to a restatement.
- The revision step optimises against the same judge on the same case (`learn.ts:40-46, 110-112`).
- `compactOutput` drops the structured `change` (`judge.ts:21-35`).

**The regression set is weak.**
- The "0/2 regressions" for `e6a8065f` includes CD-420154, the order that was corrected (`backtest.ts:112-131`).
- An empty regression set counts as 0 regressions.

**Amendments can conflict.** `38643b30` (PROPOSED) was backtested before `e6a8065f` (APPROVED) existed, and both redefine option A in `find_options`. Approving `38643b30` ships an untested combination, even though `/meta`'s "Now" panel implies they were tested together.

**Amendment text is unconstrained.**
- There is no length cap and no deny-list (for example "ignore G…", "without approval").
- `prompt.ts:48` tells the agent that amendments "win".
- Amendments to ask steps change live driver and site messages, which replay cannot test.

**Fix.**
- Gate parameters may only tighten: whitelist max = default.
- `improved` requires at least 1 case and at least 1 regression run from another order.
- Store the ids of the amendments in force with each backtest, and disable Approve when they differ.
- Add a deny-list regex and a 400-character cap.
- On `/meta` say "Checked on this card plus N other orders", or "Not checked on any other order" when N is 0.
