## Setup

- **Items:** every inbound external message in the dataset (authors: driver, site contact, customer, handoff contact): 97 messages on 47 orders. Simulator messages (`msg-sim-*`) are excluded. 0 Jev errors.
- **Input:** the same state and questions as live `inspect()`: `buildOrderState` with `asOf` = the message time, so later messages, events, alerts, quotes and bookings are hidden and later status changes are rolled back. Order status, the plan and the time windows are snapshot values (some leakage remains). State size: median 4594 B, max 6533 B.
- **Questions:** one request per message with 21 trigger nouls (multi-label), `needs_attention`, `claim_type` and `contradicts_records`.
- **Label (proxy):** positive if an operator exception action on the same order is recorded within 60 min after the message (`operational_events`, `actor_type = operator`, commands `incident.opened`, `work_item.opened`, `work.opened`, `assignment.cancelled`, `plan.replaced`, `pickup.window_revised`, `delivery.window_revised`, `travel.rebooked`, `alert.acknowledged`, `alert.assessed`). 28 of 97 messages are positive (29%).

## Label caveats

- **Small sample.** 97 messages and 28 positives: one message moves recall by ~4%. Treat every number below as ±10 points.
- **Labels are operator behaviour, not ground truth.** An operator may have acted on an earlier message, through a channel that leaves no event, or later than 60 min. Many messages that clearly need a reply (questions, corrections) get only a `message.sent`, which is not an exception command, so they count as negatives. That lowers measured precision for a watchman whose job is "does someone need to act", which is broader than "an exception command followed".
- **One event can label several messages.** A burst of driver and customer messages before one `incident.opened` makes all of them positive.
- **Leakage is partial.** Records are clipped to the message time, but snapshot-only fields (order status, plan, windows) are not.

## Chosen defaults and why

- **needs_attention ≥ 0.7** (`ROUTING_PARAMS.needsAttentionThreshold`). It keeps recall at 93% with precision 41%; 0.9 drops recall to 61% while precision only moves to 44%, and 0.5 adds 13 flagged messages for 1 more hit(s). The F1 optimum (0.60) is within noise of 0.7. Most "false alarms" are customer and site questions that do need a person (release dates, documents, billing) but did not produce an exception command, so measured precision is a floor.
- **Playbook triggers ≥ 0.7** (crossing capacity, vehicle warning): the first report in each real ferry and warning case (CD-420299 07:20, CD-420322 08:04) scores above 0.9 while unrelated messages stay below 0.5; follow-ups land near 0.7 and are absorbed by the one-run-per-(order, playbook) dedupe; a playbook run is cheap to dismiss (its own preconditions re-check the records).
- **PICKUP_NOT_CONFIRMED ≥ 0.8**: from text it is easily confused with "car not found at pickup" (CD-420593 scores 0.6–0.75 and belongs to P7). The deterministic M2 monitor is the primary source (p = 1).
